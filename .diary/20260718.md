code pass (docs-only task).

**Desktop-renderer direction** (decided in conversation, not yet built). Move
rsx-term to a native desktop GPU app; **do it in Go**, because the render is a
pure fn of the newest `Grid` → it's a render-BACKEND swap (replace the ANSI
writer with a GPU writer), reusing the entire Go model/connectors in-language —
no port. GPU via **go-webgpu** (real Mailbox, cgo → ship wgpu-native) or
**go-gl** (OpenGL + GLFW, self-contained, vsync-on/off only, no true Mailbox).
Target 60 Hz now, built on 240 Hz-ready seams (immediate-mode render,
data-rate ⟂ render-rate, alloc-free per frame, GPU instanced-quad cell grid +
glyph atlas). Why Go over Rust: model reuse dominates; GC is a non-issue with an
alloc-free render path (STW ~10–100 µs can't drop a 60/240 Hz frame; the risk is
alloc-jitter, killed by the zero-alloc discipline RSX already runs);
goroutine+channel is exactly "render newest data on arrival or a fixed tick."
Mailbox vs vsync-on: they only diverge when you render FASTER than the display
(FIFO then queues stale frames + blocks; Mailbox overwrites + shows freshest,
never blocks). A data-driven ~100 ms-update heatmap never outruns a 240 Hz
panel, so vsync-on ≈ Mailbox in practice → **go-gl vsync-on is viable**;
go-webgpu only wins if we later continuously re-render faster than data arrives.

**In flight:** an educational, honesty-first Go-vs-Rust concurrency benchmark
(fable, self-looping until cto-eval + ceo-eval + codex sign off) — the two
crossover cases (Go wins / Rust wins) with real measured p50/p99/mem numbers.
