
## 07:05 2026-07-23 — gateway egress-tile-split (GATEWAY-LATENCY follow-up)

Founder-directed: ME round-trip already sub-50µs (`bench-match-rt`,
12/17/37µs p50/p95/p99, release, in-process) — the whole job was the
gateway. Plan written in BUGS.md first, then implemented.

**Two plumbing bugs found + fixed before any measurement was possible:**
`scripts/latency-publish.sh` crashed on the expected first 404 from
`/api/bbo/{symbol}` instead of retrying (`c1e31ea`) — this alone is why
`make perf-load` had never worked. And the Go market-maker's `readLoop`
never echoed the gateway's Heartbeat, so its persistent connection died
to the 10s idle-timeout before its own `refresh_ms` (commonly >10s) ever
fired a second quote — `/api/bbo/{id}` stayed 404 forever (`f3c3904`,
mirrors `rsx-term`'s readGw/readMd echo).

**Also found, recorded not fixed:** `GW-PENDING-TIMEOUT-STRANDS-RESTING-
ORDERS` — the gateway's pending-cancel index evicts an order 10s after
submit regardless of whether it's still resting, so `Cancel` silently
"order not found"s anything older than 10s. Kept stranding the maker's
own resting orders across restarts during setup; out of scope here,
needs its own sign-off (changes pending-map lifetime semantics).

**The fix:** `rsx-gateway/src/cast_recv.rs` (new) moves the risk→gateway
casting/UDP recv off the shared monoio reactor onto its own busy-spin OS
thread (same std non-blocking pattern rsx-risk's hot loop already
proves), decoding into an owned `CastEvent` enum pushed across an `rtrb`
SPSC ring; a loopback-UDP "doorbell" wakes the monoio thread (same
readiness-dup trick already in `main.rs`). `GatewayState` stays exactly
`Rc<RefCell<..>>` — routing is unchanged, just now driven by a ring-pop
instead of the old inline `try_recv_with`. rsx-cast untouched (frozen).

**Verification:** `cargo test -p rsx-gateway` (52 tests, 9 new), `cargo
test --workspace --lib`, `cargo clippy --workspace --all-targets -D
warnings` all green. Live fault-injection (partial gw-0 restart mid-
stream) exercised real FAULTED→replay→reset_after_replay on the new
thread and the cluster recovered.

**The honest part:** built `target/release` for the first time this
session (the live cluster only ever ran debug — a 5-20x confound against
`bench-match-rt`'s release number) and added a measurement-only
`RSX_PLAYGROUND_RELEASE=1` toggle. But this box is shared and NOT quiet
(`uptime` load average ranged 8→20 across the session; unrelated
`grid_bot_*` Docker containers came and went). 8-sample before/after
medians for `match_done_to_gateway` (the targeted leg) overlap inside the
noise band (411.6µs → 539.3µs) — no confident win. The tell: the two legs
this fix does NOT touch (`gateway_to_risk`, `matching`) stayed tight and

runs — the swings elsewhere are real host contention (most plausibly
`risk`'s un-pinned busy-spin loop getting descheduled), not generic

low-noise sample did show `internal` (gw_out-gw_in) already sub-ms both

`reports/20260723_gateway-egress.md`. BUGS.md GATEWAY-LATENCY updated:
